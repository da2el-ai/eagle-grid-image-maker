## 1. 検証目的と優先順位

目的は、EagleのAPI・プレビュー・高解像度の画像合成・保存動作が、**最大32ページ／最大8,192画像**という要求を満たす設計で実現できることを確認すること。

| 優先 | 意味 | 該当領域 |
|---|---|---|
| P0 | 成立しないと主要仕様の設計を変更する | Eagle選択取得、画像処理エンジン、出力寸法・メモリ、保存ダイアログ |
| P1 | UIまたは品質に大きく影響 | 画像向き・Cover/Contain、サムネイル、テキスト配置、並べ替え |
| P2 | 性能・使い勝手・堅牢性を改善 | 設定復元、ロードキャンセル、異常系、キャッシュ最適化 |

### 推奨される最初の3検証 [優先]

1. **Eagle APIの選択順とサムネイル情報の取得**。
2. **採用画像処理ライブラリでの16×16セル高解像度合成、寸法制約、メモリピーク**。
3. **日本語を含むXYプロットの文字計測・折り返し・画像化の一致**。

## 3. API・ファイルアクセス検証

### TV-01 Eagleの選択画像と順序（P0）

- **確認すること**：`eagle.item.getSelected()` などで選択アイテムID・ファイルパス・名前・登録時刻を取得できるか。API返却配列の順序が**ユーザーの実際の選択順**と一致するか。
- **手順**：5〜20枚をA→B→Cの順に選択／逆順選択／範囲選択。結果のID列をログに出して比較。大量件数でも取得。
- **合格条件**：必要メタ情報を取得できること。「選択順」が再現できるならその条件を明記。再現不可なら**仕様要調整**として報告する。
- **成果物**：API返却サンプル（個人情報・実パスを除去）、順序比較表、所要時間。

### TV-02 サムネイル取得と`noThumbnail`の意味（P0）

- **確認すること**：公式Item APIの`noThumbnail`パラメータはどの取得処理に適用されるか。サムネイルへの実際の参照パス・URL・ファイル形式。サムネイルが生成されていない場合の挙動。
- **手順**：JPEG/PNG/WebP/GIF、縦横比違い、極端な縦長、大きな元画像を選択し返却メタデータを比較。未生成サムネイルを含める。
- **合格条件**：元画像を大量デコードせずに表示用画像へアクセスできること。失敗時のフォールバック方針が定義できること。
- **注意**：ユーザー報告の「320×418」は実例であり、サムネイル寸法の保証ではない。

### TV-03 保存先選択・連番保存（P0）

- **確認すること**：Eagle内のウィンドウ型プラグインからOSの保存ダイアログを呼び、複数ページを1回の保存操作から別ファイルに書けるか。
- **手順**：1ページ、2ページ、32ページ相当、同名ファイル存在、書き込み権限なし、ユーザーの保存キャンセルで検証。
- **合格条件**：指定保存先と連番ファイル名で保存でき、取消時に不用意なファイルが残らない。具体的な保存ダイアログのAPIを記録。
- **未決定**：連番形式、同名ファイルの扱い、途中失敗時のロールバック。

### TV-04 大量アイテムとID維持（P1）

- **確認すること**：最大8,192件のメタデータ取得、再読み込み、ID一致判定、既存編集情報の引き継ぎ。
- **手順**：新規・重複・削除済み・既存編集済みを混ぜて再取得。手動順／日時順／ランダム順で比較。
- **合格条件**：IDベースで変更状態を取り違えず、同一画像の複数表記や欠損があっても誤転記しない。

## 4. 画像処理エンジンと最大出力

### TV-05 画像処理ライブラリの動作環境（P0）

- **候補**：Node.js用**Sharp（libvips）**。採用は未決定。
- **確認すること**：Eagleが提供するNode.js／Electron環境で動くか。macOSとWindowsのネイティブバイナリ・依存関係・配布方法・起動時の読み込み。
- **手順**：各OSでインストール→読み込み→JPEG/PNG/WebP/GIF読込→リサイズ／回転／合成／書き出しを最小プラグインから実行。
- **合格条件**：両OSで配布可能な方式と再現手順が確立する。難しければ代替エンジンと比較。

### TV-06 形式・エンコーダー別の寸法上限（P0）

- **背景**：仕様上はJPEGを基準に計算し、出力形式切り替えによる超過時に警告する意図。ただしJPEGが実装上の最大とは限らない。
- **確認すること**：JPEG / PNG / WebPそれぞれについて、規格上の最大幅・高さ、採用エンコーダーの制限、最大総画素数、入力制限、計算可能サイズと実際に成功するサイズの差。
- **手順**：6,400²、16,000²、32,000² px相当のテストと、横長・縦長・ヘッダー分の加算、WebP境界寸法などを試験。利用ライブラリの安全上限も記録。
- **参考**：Sharpにはデフォルトで`limitInputPixels = 268,402,689`という入力保護設定がある（変更しうる値。バージョン依存）。これを**無制限へ変更することは推奨しない**。<https://sharp.pixelplumbing.com/api-constructor/>
- **合格条件**：各形式・各OSで安全に保存できる上限値と警告の判定式を明示できる。超過時の仕様を変更する必要がある場合はユーザー判断へ回す。
- **重要**：「警告する」は確定しているが、**保存を無効化するか**は未決定。

### TV-07 高解像度合成のピークメモリと一時容量（P0）

**理論ピクセルメモリ（RGBA、出力1ページ、セルギャップ・文字領域除く）**

| セルサイズ | 16×16の出力寸法 | 1枚の出力バッファ相当 |
|---|---:|---:|
| 400×400 | 6,400×6,400 | 約156 MiB |
| 1,000×1,000 | 16,000×16,000 | 約977 MiB |
| 2,000×2,000 | 32,000×32,000 | 約3.81 GiB |
| 4,000×4,000 | 64,000×64,000 | 約15.26 GiB |

- **確認すること**：元画像を個別に読み込んで合成する際の、RSS／ヒープ／ネイティブメモリ／一時ディスク容量／処理時間／CPU負荷／エラー率。
- **手順**：256画像／ページ、1・4・32ページ、セルサイズ段階別に計測。入力画像は縦横混在・高解像度。ページ内の合成画像を全量保持する実装と、タイル／ストリーム／一時ファイルを使う方式を比較。
- **合格条件**：目標とするセルサイズ・ページ数でOOMせず、ユーザーが許容できる時間内に保存可能な実装方式と安全上限を決定できること。
- **注意**：1枚ずつ入力をリサイズしても、最終画像全体を一度に展開する方式なら大容量のメモリが必要。実際の上限は形式上限だけで決めない。

### TV-08 GIF・回転・EXIF・透明・色（P1）

- **入力セット**：JPEGのEXIF Orientation（1/3/6/8）、透過PNG、透過WebP、アニメーションGIF、縦横混在、RGB/ICCプロファイル違い。
- **確認すること**：GIF先頭フレームだけが使用されること。画像の見た目の向きを認識した上で自動回転すること。Cover/Containと「小画像を拡大しない」の組合せが仕様どおりであること。透過と背景の扱いがJPEG/WebP/PNGで破綻しないこと。
- **合格条件**：プレビューと最終出力で**構図・向き・クロップが同じ**。出力形式の差による色の見え方が許容範囲である。

## 5. プレビュー・ページ・操作

### TV-09 サムネイルとページキャッシュ（P1）

- **比較の目安**：400×400×4バイトのデコード済みRGBA画像は**約0.61 MiB／枚**、256枚で**約156 MiB**。実際のEagleサムネイルはサイズが異なるため、**実測値とは一致しない**。
- **確認すること**：現在ページの最大256枚の読み込み速度、ページ切り替え後のメモリ解放、ページ往復によるキャッシュ増加。
- **手順**：1/256/1,024/8,192枚で起動、1→32→1など連続切り替え。倍率を上げても元画像ロードが発生しないことを確認。
- **合格条件**：ページを切り替えてもキャッシュが際限なく増えず、UIが応答する。

### TV-10 パン・ズーム・セル入れ替え（P1）

- **確認すること**：Fit倍率、ホイールズーム中心位置、ドラッグパン、Ctrl/Cmd + ドラッグによる挿入移動の正確性。
- **手順**：ズーム後にドラッグ、画面端・重なり、1ページ目→2ページ目の境界、1/256枚、削除モードON時、macOSとWindowsの修飾キーを検証。
- **合格条件**：誤って通常ドラッグが並び替えにならず、指定位置への挿入移動が正確。表示順と書き出し順が一致する。
- **未決定**：ページをまたぐドラッグ中のページ切り替えジェスチャー。

### TV-11 レイアウト計算の共有（P1）

- **確認すること**：セル座標・回転・Cover/Contain・端数・余白・文字が、プレビューと出力で同じレイアウト結果から描画されるか。
- **手順**：プレビューを400×400基準で作り、出力サイズの異なるページと座標・境界線・crop範囲を比較。
- **合格条件**：プレビューと出力で配置順、余白比率、クロップ範囲が一致。個別の描画処理に重複したレイアウト計算を持たない。

## 6. テキスト／XYプロット

### TV-12 日本語フォントと折り返し（P0/P1）

- **確認すること**：実装環境でのフォント列挙・指定、フォントが存在しない場合の代替、幅計測、混在文字（日本語・英数字・記号）、個別列ヘッダーの折り返し、行ヘッダーの最大100em幅。
- **手順**：短・長ラベル、空文字、漢字・かな・絵文字を含む例を使い、タイトル／行ヘッダー／列ヘッダー／軸タイトルを比較表示。
- **合格条件**：テキストが切り抜かれず、幅・高さ・配置が一貫。プレビューと高解像度出力の行送り・折り返しが許容範囲で一致。
- **未決定**：行ヘッダーの共通幅、列ヘッダーの共通高さ、軸タイトルの向き、ページごとのヘッダー再掲。

## 7. 永続化・エラー・操作フロー

### TV-13 設定のみの復元（P2）

- **確認すること**：グリッド・画像・テキスト・外観・出力設定を保存し、再起動で復元。**画像セットそのものは復元しない**。
- **手順**：画像Aを選択して設定変更→閉じる→Eagleで画像Bを選択→再起動。
- **合格条件**：設定は保持され、プレビューの画像はBに切り替わる。

### TV-14 上限と異常系（P1）

- **ケース**：0枚、上限ちょうど、上限+1、破損画像、見つからない元画像、OS権限不足、保存先ディスク不足、ページ保存途中の失敗、再読み込み中の閉じる操作。
- **合格条件**：アプリが固まらない／不完全ファイルの状態が分かる／Eagleの元画像を変更しない。
- **未決定**：スキップ・中断・既存ページを残すルール。

### TV-15 ソートとランダムの状態（P2）

- **確認すること**：ファイル名の昇降順、日本語ファイル名・同名時の安定性、登録時刻の昇降順、ランダムの1回だけのシャッフル、手動並び替えでの状態変更。
- **手順**：同名・同時刻・全角文字・数字入りファイル名でケース作成。ランダム→Fit→ページ切り替え→再読み込み→別ソート→ランダムを試す。
- **合格条件**：画面表示の並び順と内部順序が一致し、ランダムは別ソート選択後の再選択以外で不用意に再実行されない（再読み込み時の挙動は先に決定）。

### 10.2 項目ごとの結果

**TV-01 選択順**

- Cmd クリック：クリックした順
- Shift クリック：始点から終点の順
- 全選択：表示の先頭から末尾の順。ソートを逆順にしても、ソート後の先頭から末尾
- `get({isSelected: true})` も同じ順番を返す
- `eagle.item.select(ids)` で選ぶと、渡した順番がそのまま取得順になる。`select([])` では選択を解除できない（存在しない ID を渡すと解除される）
- 取得できる項目：`id`・`name`・`ext`・`width`・`height`・`size`・`importedAt`・`modifiedAt`・`noThumbnail`・`noPreview`・`filePath`・`fileURL`・`thumbnailPath`・`thumbnailURL`
- `width` / `height` は EXIF の向きを反映した見た目のサイズ
- 結論：仕様の「選択順」は `getSelected()` の順番をそのまま使えば実現できる

**TV-02 サムネイル**

| 元画像 | サムネイル |
|---|---|
| 長辺 960px 以下（JPEG・WebP・小さい PNG） | 作られない。`noThumbnail: true` で、`thumbnailPath` は元画像そのもの |
| 長辺 980px 以上 | 短辺 320px に縮小。例：1200×1200 → 320×320、6000×4000 → 480×320 |
| 細長い画像 | 短辺を 320px まで**拡大**する。例：1000×100 → 3200×320、300×2000 → 320×2133 |
| 約 1MB を超える PNG | 960px 以下でも作られる（600×600・1.08MB で作られた） |
| GIF | 300×200 でも作られた |

- サムネイルの拡張子は `.png` だが、中身は WebP。拡張子で形式を判断しない
- 960px と 980px の間の境目と、PNG のファイルサイズの境目は細かく調べていない

**TV-03 保存**

- 保存ダイアログは `eagle.dialog.showSaveDialog` で開ける
- 連番は `grid_01.png` の形で保存できた。1ページだけなら `grid.png`
- 同名ファイルがあるときの3通り（中止・上書き・別の番号 `grid-2_01.png`）が動いた
- 途中で失敗したとき、後片付けありなら書いたページを消せる。なしなら残る
- 書き込めない場所では `Operation not permitted` のエラーを受け取れる

**TV-06 形式ごとの上限**（単色の画像で計測）

| 寸法 | JPEG | PNG | WebP |
|---|---|---|---|
| 6400² | 0.2 秒 | 0.2 秒 | 1.3 秒 |
| 16000² | 1.1 秒 | 0.4 秒 | 8.0 秒 |
| 16383² | 成功 | 成功 | 成功（8.2 秒） |
| 16384² | 成功 | 成功 | **失敗** |
| 32000² | 成功（5.6 秒） | 成功 | 失敗 |
| 65500×1000 | 成功 | 成功 | 失敗 |

- WebP は幅・高さとも 16383 px が上限
- 16384² 以上の画像は、sharp の既定の制限（`limitInputPixels`、約 2.68 億画素）では読み戻せない。書き出しの土台の画像にもこの制限がかかるので、土台だけ制限を広げる必要がある

**TV-07 16×16 の合成**（基本セット 13 枚を繰り返して 256 セル）

| セル | 方式 | 形式 | 時間 | ファイル | 一時容量 |
|---|---|---|---|---|---|
| 400 | memory | JPEG | 4.1 秒 | 1.8 MiB | 0 |
| 400 | tempfile | JPEG | 4.9 秒 | 1.8 MiB | 9.8 MiB |
| 400 | strip | JPEG | 4.2 秒 | 1.8 MiB | 9.2 MiB |
| 400 | memory | PNG | 6.2 秒 | 6.5 MiB | 0 |
| 400 | memory | WebP | 7.9 秒 | 1.0 MiB | 0 |
| 400 | memory | JPEG・3ページ | 12.1 秒 | 各 1.8 MiB | 0 |
| 1000 | memory | JPEG | 10.2 秒 | 6.3 MiB | 0 |
| 1000 | strip | JPEG | 11.2 秒 | 6.3 MiB | 62 MiB |
| 1000 | tempfile | PNG | 24.9 秒 | 44.7 MiB | 53 MiB |

- メモリ：セル 400 の memory 方式で RSS が約 530MB 増え、セル 1000 で約 1.3GB 増えた
- sharp が確保したメモリは、処理が終わってもほとんど OS に返されなかった（RSS は約 2.5GB のまま）。このため、2回目以降の計測のピーク値は前の処理の分を含んでいる
- 3つの方式の出力は、透過の丸めで最大 1/255 の差

**TV-08 向き・透過・GIF**

- EXIF の向き（1/3/6/8）・透過 PNG / WebP・アニメーション GIF の先頭フレーム・Cover / Contain を、プレビューと出力で並べて目で見た。問題なし
- PNG / WebP で書き出すと、背景が不透明でもアルファチャンネル付きになる

**TV-09 ページキャッシュ**

- 1,024 件（4 ページ）で、最初のページの表示まで 333ms
- ページの往復は 24〜208ms。キャッシュは最大 256 枚（1ページ分）で増え続けない
- 6 倍まで拡大しても、新しいファイルの読み込みは 0 件

**TV-10 操作**

- パン、ポインターの位置を中心にしたホイールでのズーム（ずれ 0.2px 以下）、Cmd / Ctrl + ドラッグでの挿入移動（前へも後ろへも）が正しく動いた
- ドラッグ中にページ送りボタンの上で止まると、ページが切り替わった
- 削除モードで確認ダイアログを出してから外せた
- 描画は平均 1.7ms

**TV-12 文字**

- `queryLocalFonts()` は Eagle 内で使え、413 フォントが取れた
- Canvas と sharp（Pango）で文字幅を比べると、英数字で最大 16% 違った（日本語は 1% 以内）。このため、書き出しの文字は Canvas で描いて合成する方式にした
- 書き出しの倍率を 1 倍・2 倍にしても、折り返しの位置は変わらなかった
- カラーの絵文字はプレビューと出力の両方で表示された

**TV-14 異常系**

- 選択 0 件：`getSelected()` は空の配列を返す
- 元画像がない：`Input file is missing`
- 壊れた画像：sharp は `corrupt header`、`<img>` は `cannot be decoded` のエラーになる
- 書き出しの前後で、元画像のハッシュは変わらなかった

**TV-15 並べ替え**

- `Intl.Collator('ja', { numeric: true })` での名前順：`Ａ全角 → img_02 → img1 → img2 → IMG3 → img10 → 画像ア → 画像あ → 画像亜 → 同名 → 同名`
- 全角英字は半角と同じ扱いになる。大文字と小文字は区別しない。数字は数の大きさで並ぶ
- ランダムは、ランダムを選んだときだけ並べ替わった。Fit・ページ切り替え・同じ値の選び直し・再読み込みでは変わらない

- セル 2000 以上（32000² 以上）の 16×16 の合成

- 保存先のディスクが足りないとき

### 10.4 仕様を決める必要がある点

1. **プレビューの基準の大きさ**：サムネイルは短辺 320px なので、仕様の「400×400 基準」ではセルを埋めるときに少し拡大される。また、長辺 960px 以下の画像はプレビューでも元画像を読む
2. **ページをまたぐ挿入の位置**：2ページ目の先頭の前に落とすと、並びの上では1ページ目の最後に入る。落とした場所と、表示される場所が違う
3. **sharp のメモリ**：一度確保したメモリが返されないので、続けて書き出すとメモリの使用量が高いまま残る。書き出しを別のプロセスで行うかどうかを決める。なお Windows では、処理が終わるとメモリが OS に返された（11.2 の TV-07）。この問題は主に macOS で起きる
4. **行ヘッダーの幅**：一番長い行ヘッダーに合わせて全行で共通の幅にすると、短い行ヘッダーの左に大きな余白ができる

2026-11-23 にユーザーが決めた（全体仕様書 v0.3 に反映）。

1. プレビューの基準を 320×320 にし、セルの大きさの初期値も 320×320 にする。プレビューで拡大してぼやけるのは許容する。長辺 960px 以下の画像は、プレビューでも元画像を使う
2. 落としたページの先頭に入れる。あふれた画像は次のページへ押し出す
3. 初期版では、sharp のキャッシュと並列数を絞ってピークを下げる。別のプロセスで書き出す方法は、メモリが実際に問題になったら検討する
4. 全行で共通の幅にして右寄せにする。短い行ヘッダーの左の余白は許容する

### 11.2 macOS と違った点

**プラグインのフォルダのパス**

- ページの URL は `eagleplugin://<プラグインID>//D:/…/index.html` の形で、ドライブ名の前に `/` が2つ付く
- URL のパスから先頭の `/` を1つだけ取ると `\\D:\…` になり、ネットワーク上の場所とみなされてファイルを開けない（`UNKNOWN: unknown error`）
- ドライブ名の前の `/` は、いくつあってもすべて取る必要がある

**TV-02 サムネイルの境目**

| 元画像 | サムネイル |
|---|---|
| 長辺 960px 以下 | 作られない（JPEG・WebP・単色の PNG） |
| 長辺 970px 以上 | 短辺 320px に縮小 |
| PNG（ノイズ画像） | 988 KiB では作られず、1,057 KiB では作られた。境目は約 1 MiB |
| GIF | 小さくても作られる。100×100 の GIF は 100×100 のままで、拡大されない |

- サムネイルの拡張子が `.png` で中身が WebP であること、細長い画像は短辺を 320px まで拡大することは、macOS と同じ

**TV-03 保存**

- 連番・同名ファイルの3通り・途中の失敗と後片付けは、macOS と同じように動いた
- `C:\Windows\System32` に書くと失敗した（Eagle は管理者としては動いていない）
  - Node の `fs` で書くと `EPERM` を受け取れる
  - sharp の `toFile` のエラーは、Windows の説明の部分が文字化けして読めない（`unable to open for write` のあとが化ける）。sharp で `toBuffer` してから `fs` で書くと、エラーの種類で判断できる
  - `fs.access(W_OK)` は、書けない System32 でも成功を返す。Windows では読み取り専用の属性しか見ないので、書けるかどうかの事前チェックには使えない
- `eagle.app.getPath('desktop')` が、OneDrive の下のデスクトップを返す環境がある

**TV-07 16×16 の合成**（基本セット 14 枚を繰り返して 256 セル、並列数は macOS に合わせて 10）

| セル | 方式 | 形式 | 時間 | ファイル | 一時容量 |
|---|---|---|---|---|---|
| 400 | memory | JPEG | 2.7 秒 | 1.9 MiB | 0 |
| 400 | tempfile | JPEG | 3.6 秒 | 1.9 MiB | 9.9 MiB |
| 400 | strip | JPEG | 2.9 秒 | 1.9 MiB | 9.7 MiB |
| 400 | memory | PNG | 4.1 秒 | 6.9 MiB | 0 |
| 400 | memory | WebP | 3.9 秒 | 1.0 MiB | 0 |
| 400 | memory | JPEG・3ページ | 8.1 秒 | 各 1.9 MiB | 0 |
| 1000 | memory | JPEG | 7.0 秒 | 6.4 MiB | 0 |
| 1000 | strip | JPEG | 7.8 秒 | 6.4 MiB | 62 MiB |
| 1000 | tempfile | PNG | 17.8 秒 | 44.5 MiB | 52 MiB |

- メモリのピークは、セル 400 で RSS 約 700MB、セル 1000 で約 2.8GB
- 全部終わったあと、RSS は約 290MB に戻った。macOS では約 2.5GB のまま戻らなかった。TV-06 でも、ピークが 6GB になったあとで次の計測の開始時は約 250MB に戻っていた

**TV-12 文字**

- 既定の `sans-serif` はメイリオ（Meiryo）になった。`serif` は游明朝、`system-ui` は Yu Gothic UI
- `queryLocalFonts()` は使え、101 フォントが取れた
- Canvas と sharp（Pango）の文字幅の差は、英数字で最大 22%、**日本語でも 10〜16%** あった（macOS では日本語は 1% 以内）。書き出しの文字を Canvas で描いて合成する方式は、Windows ではなおさら必要
- 書き出しの倍率を 1 倍・2 倍にしても、折り返しの位置は変わらなかった。カラーの絵文字も出力された

**TV-14 異常系**

- エラーの内容（`Input file is missing`、`corrupt header`、`cannot be decoded`）は macOS と同じ
- 空きディスク容量：`wmic` がこの Windows 11 には入っていない（`where wmic` でも見つからない）
  - PowerShell の `Get-PSDrive` / `Get-CimInstance Win32_LogicalDisk` なら取れる（250〜450ms）
  - `fsutil volume diskfree` は管理者の権限が要るので失敗した
  - Node 16 には `fs.statfs` がない
- sharp で読んだファイル・書いたファイルは、すぐ名前の変更・上書き・削除ができた（sharp のキャッシュを切った状態で確認）

**その他**

- Git Bash から `curl` で日本語を含む JavaScript を引数で送ると、文字化けした。UTF-8 のファイルにしてから送ると正しく届いた（検証の道具の話で、本番には関係しない）

### 11.3 実装で気をつけること

1. プラグインのフォルダのパスは、URL の形に頼らずに求める。URL から求める場合は、ドライブ名の前の `/` をすべて取る
2. 書き出しのエラーは、sharp のメッセージをそのまま表示しない。`toBuffer` のあとに `fs` で書くなどして、エラーの種類で表示を決める
3. 空きディスク容量を取るなら、Windows では PowerShell を使う
4. sharp のメモリの問題（10.4 の 3 点目）は、主に macOS で起きる
